# 开发者指南

面向想构建、修改或发布 GitDock 的人。终端用户请读 [README](../README.md)；当前状态、验证记录与已知限制在 [docs/05-交接文档.md](05-交接文档.md)。

> 命名：产品名 GitDock，仓库目录名仍是 `git-graph`，文中的“Git Graph”指图谱视图/模块，与 VS Code 的 Git Graph 扩展无关。

## 技术栈

| 层 | 选型 |
|---|---|
| 桌面壳 | Tauri 2 |
| 前端 | React 18 + TypeScript 5.6 + Vite 5 |
| 图谱布局 | 纯函数 crate `graph-layout` |
| 只读 Git | gix（只读） |
| 写操作 | Git CLI（参数数组，固定工作目录，不经 shell） |
| 语言 | Rust stable（workspace 要求 1.85+） |

## 环境要求

- Windows 10/11，WebView2 运行时
- Node.js >= 24.0.0，npm >= 11.0.0（CI 使用 Node 24）
- Rust stable，附带 `rustfmt` 与 `clippy` 组件（建议用 [rustup](https://rustup.rs/) 安装）
- Git >= 2.30.0（低于该版本只读可用、写操作禁用）
- Tauri 的 Windows 构建依赖：MSVC 构建工具与 Windows SDK，详见 [Tauri prerequisites](https://tauri.app/start/prerequisites/)

## 常用命令

```bash
npm install      # 前端依赖
npm run check    # 本地门禁：前端构建 + cargo fmt --check + clippy -D warnings + workspace 测试
npm run tauri dev -- -- -- "C:/path/to/repo"   # 开发运行并指定仓库
npm run tauri build -- --bundles nsis          # 打安装包
```

完整的开发/调试/夹具/运行期文件路径说明见 [docs/05 §7](05-交接文档.md#7-环境构建与运行)。两条容易踩的：

- **验证 release 界面不要用 `cargo build --release`**：tauri 仍会按 dev 模式编译，窗口去连 `localhost:1420` 停在错误页上。用 `npm run tauri build -- --no-bundle`（跳过安装包，约 1 分钟）才是嵌入 `dist/` + 生产 CSP 的二进制。
- 重打包前先退出正在运行的 `gitdock-app.exe`，否则 Windows 锁住产物。

## 目录结构

```text
src/                    # 前端
  app/                  # 会话、分栏、写流程与外壳组件
  features/graph/       # 图谱虚拟列表、行渲染、悬浮卡、分页
  features/detail/      # 提交详情、文件 diff、语法高亮、并排分栏
  features/compare/     # 双槽、对比弹窗、文件与 commit 列表
  features/search/      # 搜索弹框与候选生成
  features/settings/    # 外部工具、监听、外观、快捷键、关于与反馈
  features/write/       # 写确认框与结果展示
  shared/               # IPC 唯一入口、DTO 类型、通用 UI
  styles/               # 按层叠顺序 @import 的样式片段
crates/
  git-core/             # 公共 DTO、Oid 校验、错误码、cursor
  git-read/             # GitReadModule 与 gix adapter（只读）
  graph-layout/         # 图谱 lane 纯函数
  git-write/            # GitWriteModule、写前 Gate、CLI adapter
  refresh/              # RefreshCoordinator（generation 与旧结果丢弃）
  fixture-gen/          # 测试夹具生成
src-tauri/              # Tauri command、会话状态、监听、配置与日志
docs/                   # 架构、任务拆分、验证记录与交接文档
```

## 开发约束

- gix 只读；所有写操作（cherry-pick / revert / switch 等）必须走 Git CLI 的参数数组，不经 shell。
- 前端不执行任意命令、不拼接 shell、不访问 `.git` 内部路径、不解析 Git 对象；网络请求一律在 Rust 侧发出（生产 CSP 的 `connect-src` 只允许 `ipc:`）。
- 状态类命令使用 `GIT_OPTIONAL_LOCKS=0`，避免创建 `index.lock` 触发刷新自激循环；该变量不得用于写操作。
- 写操作前先过 Gate；冲突后只展示状态与终端提示，绝不自动 `--abort` / `--quit`。
- `index.html` 不写内联 `<style>` / `<script>`：生产 CSP 会因此给 `style-src` 追加 nonce，令行内样式全部失效。
- 可改键只有终端开合与缩放三档，键位存在 WebView `localStorage` 的 `gitdock.keybindings`（不进 `settings.json`，随 WebView 数据一起清掉）；`Esc` 的逐层退出与控件内 `↑↓/Enter` 是固定的无障碍语义，不做成可配置项。
- 只实现需求文档定义的范围，不扩展 P1/P2；不复制参考项目的代码、资源、样式或测试夹具。

## 发布新版本

1. 版本号用一条命令写齐：`npm run bump -- 0.2.0`（`scripts/version.mjs`）。它同时写根 `Cargo.toml` 的 `[workspace.package]`（所有 crate 继承它，界面「关于」与版本检查用的 `env!("CARGO_PKG_VERSION")` 也取自这里）、`Cargo.lock` 的 8 个 workspace 成员、`package.json` / `package-lock.json`、`src-tauri/tauri.conf.json`（安装包文件名与 exe 的 FileVersion/ProductVersion）。`npm run check` 的第一步就是它的 `--check` 模式，漏改任何一处直接失败。发布流程不自动 bump，改版本是独立提交。
   - 为什么不是「一个变量」：cargo 与 npm 各有自己的版本字段，没有共享变量机制。Tauri 的 `version` 确实可以省略（回落到 Cargo.toml）或写成某个 `package.json` 的路径，但省略后 tauri-build 就不再往 Windows 资源里写 FileVersion/ProductVersion，安装包属性里看不到版本号；所以保留显式声明，由脚本统一维护。
2. 打附注标签并推送：`git tag -a v0.2.0 -m "..." && git push origin v0.2.0`。
3. `.github/workflows/release.yml` 仅在 `v*` tag 上触发：先校验声明的版本号等于 tag（不一致直接失败，不打包；脚本只保证各处一致，不认 tag），再 `npm run tauri build -- --bundles nsis`，最后用 `gh release create` 发布；重跑同一 tag 走 `upload --clobber`，不会删除已发布的 Release。tag 名含 `-`（如 `v0.2.0-rc.1`）会自动标为预发布，不占用 `releases/latest`。
4. 日常 push 只跑 `ci.yml`（`npm ci` + `npm run check`），与本地门禁同一套 `scripts/verify.mjs`。
5. 安装包**未做代码签名**，用户侧会有 SmartScreen 提示；签名条件与可选路径见 [docs/05 §10](05-交接文档.md)。
6. 应用内的版本检查读取 `https://api.github.com/repos/zyTheGit/gitdock/releases/latest`：仓库未公开或还没有 Release 时返回 404，匿名访问超限返回 403，两者都在界面行内提示，不影响其他功能。
