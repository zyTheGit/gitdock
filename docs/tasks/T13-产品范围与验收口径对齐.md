# T13：产品范围与验收口径对齐

- **波次**：Wave 0（产品口径）
- **优先级**：P0
- **前置依赖**：无
- **是否需要 ADR**：否（仅文档与验收记录）
- **可并行性**：可与代码任务并行，但应在 T14 前完成产品范围定稿
- **粗略成本**：1 人日

---

## 1. 背景与目标

`docs/01-需求冻结.md` 仍描述单窗口单仓库，并排除远程写、分支、stash、merge/rebase；`需求文档.md` 也有过期口径。GUI 验收清单的版本基线早于当前实现，部分项目与交接文档中的 release 实测记录不一致。

目标不是重写历史，而是让读者能区分：

- 历史 MVP 冻结范围。
- 当前已实现产品范围。
- 已通过 CI 的能力。
- 已有 release 实测证据的能力。
- 仍待用户实机验收的能力。

---

## 2. 范围与边界

### In Scope

1. 将 `docs/01-需求冻结.md` 标记为历史 MVP 基线，在开头增加当前产品范围指针，保留原始决策作为历史记录。
2. 更新 `需求文档.md` 中与现状冲突的单仓、单窗口、远程写、分支、stash、merge/rebase 排除项。
3. 对齐 `docs/verification/GUI-实机验收清单.md` 的适用版本、更新日期和验收状态。
4. 在 `docs/05-交接文档.md` 中建立“当前产品范围”和“待验收能力”的统一入口，消除底部过期下一步造成的误读。
5. 核对 `docs/assets/screenshots/` 的截图清单：标记旧图、缺失图和可复用图；只有取得当前 release 截图后才能替换。
6. 为每条已勾选的 GUI 验收项补充可追溯证据（提交号、release 实测日期或验证文档章节）。

### Out of Scope

- 不修改任何产品代码。
- 不把缺少证据的验收项直接勾选为通过。
- 不删除历史 ADR、历史决策或旧截图。
- 不宣称 macOS / Linux 已获得未实机验证的正式支持。

## 4. 关键约束

- 历史文档与当前状态分开表达，不用当前功能覆盖历史决策语义。
- “代码已实现”“CI 通过”“release 实测通过”“用户实机验收通过”必须使用不同状态词。
- 所有验收证据必须可追溯到具体提交、日期、环境或验证文档。
- 不虚构未执行的实机操作。

---

## 5. 实施步骤

1. 汇总 README、`docs/03`、`docs/11`、`docs/13` 和当前代码中的产品范围。
2. 将 `docs/01` 改为历史基线说明，并增加当前范围链接。
3. 更新 `需求文档.md` 的过期边界。
4. 逐项核对 GUI 清单与交接文档中的 release 记录，补齐证据或撤销无证据勾选。
5. 更新截图维护清单，明确哪些图需要重拍。
6. 复核所有文档中的版本号、状态词和下一步描述。

---

## 6. 验收标准

- **Given** 新读者首次打开 `docs/01`，**When** 阅读产品范围，**Then** 能明确它是历史 MVP 基线，并能跳转到当前产品范围。
- **Given** 阅读 `需求文档.md`，**When** 查找仓库数量、远程写、分支、stash、merge/rebase 能力，**Then** 不再与当前 README 和代码事实冲突。
- **Given** 查看 GUI 验收清单，**When** 判断某项是否已验收，**Then** 每项都有明确状态和证据，不依赖读者推测。
- **Given** 查看截图清单，**When** 选择产品展示图，**Then** 能识别当前有效图与待更新图。
- **Given** 检索“下一步”，**When** 阅读交接文档，**Then** 不再把已完成路线描述成待实施任务。
