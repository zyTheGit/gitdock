# T20：操作反馈与恢复入口统一

- **波次**：Wave 2（核心工作流补强）
- **优先级**：P1
- **前置依赖**：T14、T15
- **是否需要 ADR**：否（复用既有结果 DTO 和恢复入口）
- **可并行性**：依赖 T14 / T15 完成后，可与 T18、T19 并行
- **粗略成本**：3–5 人日

---

## 1. 背景与目标

当前成功反馈主要是单一字符串 toast，错误详情和恢复入口分散在不同对话框与横幅中。用户需要理解“发生了什么、影响了谁、下一步能否恢复”。

目标：统一操作通知结构和恢复入口，同时保留 Gate、危险二次确认和已有写流程。

---

## 2. 范围与边界

### In Scope

1. 将应用级通知扩展为结构化模型：
   - 成功 / 警告 / 错误。
   - 标题与摘要。
   - 可选详细说明。
   - 可选 stderr 折叠详情。
   - 可选上下文恢复动作。
2. 首批覆盖：
   - commit / amend。
   - reset。
   - discard。
   - stash save / apply / pop / drop。
   - fetch / pull / push。
   - 分支重命名与远程删除部分失败。
3. 成功通知沿用现有自动消失策略；错误和需要恢复的通知常驻至用户关闭或离开仓库。
4. 恢复动作只调用既有安全入口：
   - 普通 commit → 定位新 HEAD。
   - amend / reset → Reflog。
   - Stash 冲突 → 冲突文件。
   - Pull / Push 失败 → Fetch / Pull 引导。
   - 远程删除部分失败 → 保留当前错误和本地结果说明。
5. 复用 `GateReportView` 的语义，减少确认框中的重复 Gate 渲染，但不改变确认条件。
6. 更新双语文案和通知样式。

### Out of Scope

- 不实现通用 Git Undo。
- 不自动 stash、reset、clean、abort、continue 或 skip。
- 不删除 hard reset、discard、amend、stash drop 等专用危险确认。
- 不改变写请求、Gate 结果或错误码。
- 不把所有 stderr 直接塞进主提示；主提示保持可读，原始详情折叠。

## 4. 关键设计约束

- 通知动作必须复用既有回调，不得绕过 `useWriteFlow` 或直接调用 IPC。
- 恢复动作不可用时不得展示为可点击按钮。
- 执行中通知不得诱导重复提交。
- 原始 stderr 只作为详细信息展开，不覆盖主错误摘要。
- 通知层级高于遮罩，但不能阻断底层仍在执行的写流程。
- 不增加通知动画。

---

## 5. 实施步骤

1. 盘点首批写流程当前的成功、失败和恢复路径。
2. 定义结构化通知模型和统一展示组件。
3. 将 `toast` 状态迁移为新模型，保留现有调用点的渐进替换。
4. 为首批操作接入摘要、stderr 详情和恢复动作。
5. 复用 Gate 展示组件，清理重复结构而不改变确认语义。
6. 验证成功、拒绝、执行失败、部分成功、冲突和恢复动作。

---

## 6. 验收标准

- **Given** commit 成功，**When** 查看通知，**Then** 能看到动作、目标和新 HEAD 定位入口；amend / reset 成功时提供既有 Reflog 入口。
- **Given** discard 或 hard reset 被拒绝，**When** 查看结果，**Then** Gate 原因保持清晰，专用危险确认和勾选要求没有被弱化。
- **Given** stash pop / apply 产生冲突，**When** 查看通知，**Then** 可直达冲突文件，不自动继续或中止。
- **Given** push 被 non-ff 拒绝，**When** 查看通知，**Then** 主提示说明失败，stderr 可折叠查看，并提供 Fetch / Pull 引导。
- **Given** 本地删除成功但远程删除失败，**When** 查看通知，**Then** 明确说明本地结果和远程失败，不把整体误报为完全成功。
- **Given** 通知包含恢复动作，**When** 动作不可用或 busy，**Then** 按钮禁用并显示原因。
- **Given** 执行 `npm run check`，**When** 校验结束，**Then** 全部门禁通过，触及文件满足行数限制。
