# F1-1 性能基线（5 万提交）

- 日期：2026-10-28（后端）、2026-11-13（前端端到端与 10 万 commit 内存）
- 被测代码：`7c12c26` + `crates/git-read/tests/perf_baseline.rs`；端到端部分为 `67eb4bc` + 工作区（release 构建）
- 结论：**后端首屏合计 504 ms；release 包端到端首屏 50k 冷 941 ms / 温 939 ms、100k 冷 1017 ms / 温 1041 ms，均在 1.5 s 内；10 万 commit 常驻内存峰值 457.5 MB，满足 ≤ 500 MB（余量 42.5 MB）**

## 1. 环境

| 项 | 值 |
|---|---|
| 机器 | Intel Core Ultra 5 125U / 15.5 GB |
| 系统 | Windows 10.0.26300 |
| Rust | 1.99.1（release 构建） |
| Git | 2.53.0.windows.2 |
| 仓库 | `target/test-fixtures/perf-50k/perf`，50 000 提交、线性历史、单文件 `file.txt` |

## 2. 方法

- 夹具由 `fixture_gen::generate_perf` 使用 `git fast-import` 生成，首次运行后缓存，不计入测量。
- 每轮运行前清空索引磁盘缓存目录，保证冷启动可复现；打开模块时传入 `cache_dir`，与桌面端一致。
- 测量点：
  - 打开仓库：`GitReadModule::open`（gix 发现 + 版本探测）。
  - 读取状态：`state()`。
  - 首屏第一页 / 后续页：`read_graph_page(Head, cursor, 200)`，含索引构建、布局与 200 条摘要。
  - 温启动首屏：同一缓存目录重新 `open` 后读第一页，模拟应用重启。
- 断言：首屏合计（打开 + 状态 + 第一页）≤ 1500 ms；每页 200 条；布局行与提交一一对应；线性历史单 lane；翻页不重叠。

复现命令：

```bash
cargo test -p git-read --release --test perf_baseline -- --ignored --nocapture
```

## 3. 结果

| 阶段 | 耗时 |
|---|---|
| 打开仓库 | 48.9 ms |
| 读取状态 | 23.8 ms |
| 首屏第一页（冷缓存） | 431.4 ms |
| **首屏合计** | **504.1 ms（预算 1500 ms，余量 66%）** |
| 同一实例重复首屏 | 68.2 ms |
| 第 2 页 | 68.8 ms |
| 第 3 页 | 69.4 ms |
| 温启动首屏（磁盘缓存命中） | 72.5 ms |

测试整体耗时 2.33 s（含 50 000 提交夹具生成与三轮翻页校验）。

## 4. 解读与限制

- 冷启动主要成本在首次构建 5 万条索引（约 431 ms）；磁盘缓存命中后首屏降到 72.5 ms，翻页稳定在约 69 ms。
- 该数字**只覆盖 Rust 后端**（IPC command 返回分页数据），不含前端 React 渲染与虚拟滚动的首帧时间；端到端首屏已在 release 包上实测，见第 6.4 节（50k 冷 941 ms / 温 939 ms，100k 冷 1017 ms / 温 1041 ms）。
- 常驻内存与 10 万 commit 场景已在第 6.4 节补齐：10 万峰值 457.5 MB（主进程 + WebView2 子进程），5 万参考 439.2 MB。采样时同机运行着另一个 GitDock release 实例，内存按 `ParentProcessId` 只计入被测实例的 `msedgewebview2` 后代；图谱索引磁盘缓存与另一实例共用，故实测以中位数与温/冷对照为准。
- 端到端首屏主要由进程与 WebView2 启动占据：50k 冷温差距 < 3 ms、100k 冷温差距约 24 ms，说明 10 万条索引的构建在 release 预算内可忽略。
- 夹具为线性历史，未覆盖大量分支/合并导致的 lane 与待连接边增长场景；该类布局性能由 `graph-layout` 单测与后续大分支夹具补足。
- 结果对机器与磁盘状态敏感；CI 上仅运行 `--ignored` 之外的测试，性能基线需在目标机器手动执行并记录。

## 5. 后续建议

1. 增加带 1000 条分支与 merge 结构的 5 万提交夹具，观测布局与 refs 摘要成本。
2. 若要压低端到端首屏，优化点在进程与 WebView2 启动（约 0.9 s 地板），而非索引构建。
3. 若引入索引缓存淘汰策略，需复核冷启动预算。

## 6. 前端端到端测量方法（已执行，2026-11-13）

> **状态：已执行。** 本节方法保持可复现；结果见 6.4。F1-1 的「前端首屏」与「10 万 commit 内存」两项按 6.4 判定标准通过。

### 6.1 前置与夹具

- **必须用 release 构建**：`npm run tauri build`，产物 `target/release/gitdock-app.exe`。dev 模式会掩盖 CSP、终端接管与部分 WebView2 行为差异，不能用于本测量。
- **5 万提交夹具**：运行第 2 节的后端基线一次即可生成并缓存到 `target/test-fixtures/perf-50k`（`fixture_gen::generate_perf`，`crates/fixture-gen/src/lib.rs`）。
- **10 万提交夹具**：仓库没有现成 CLI 入口（`cargo run -p fixture-gen` 的 `generate_all` 不生成 perf 仓库）。复制 `crates/git-read/tests/perf_baseline.rs` 的 `stage()` 逻辑，把 `COMMITS` 改为 `100_000`、输出目录改为 `target/test-fixtures/perf-100k`，作为临时 `#[ignore]` 测试执行一次；**不要提交该临时测试**。底层仍是 `git fast-import`，生成耗时不计入测量。
- **固定条件**：同一台机器、同一 Git 版本（`git --version` 记录）、同一 release 构建；关闭其他 WebView2 应用，避免 RSS 与调试端口串扰。
- **冷 / 温口径**：冷启动前删除应用缓存目录下的 `graph-index`（`src-tauri/src/app/state.rs` 的 `index_cache_dir`）；温启动保留该目录。两种都要记录。

### 6.2 启动到图谱首帧

1. 设置调试端口并记录启动墙钟（PowerShell）：
   ```powershell
   $env:WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS = '--remote-debugging-port=9222'
   $t0 = Get-Date
   $p = Start-Process target/release/gitdock-app.exe -ArgumentList "<夹具仓库绝对路径>" -PassThru
   ```
   （与 `docs/verification/阶段A-终端Spike.md`、`docs/05-交接文档.md` §7.3 的 CDP 启动方式一致。）
2. 以 `scripts/cdp.mjs` 为模板写一次性轮询脚本（不入库）：每 25–50 ms 连接 `http://127.0.0.1:9222/json` 找到 page target，执行
   `(async () => { await new Promise(r => requestAnimationFrame(() => requestAnimationFrame(r))); return document.querySelectorAll('[data-oid]').length })()`
   （`requestAnimationFrame` 双帧等待；图谱行由 `src/features/graph/GraphRow.tsx` 输出 `data-oid`）。
3. 第一次读到行数 > 0 的时刻记为 `$t1 = Get-Date`；**端到端首屏 = t1 − t0**，精度为轮询间隔（±25–50 ms，相对 1500 ms 阈值可接受）。同时记录页面内 `performance.now()` 作为交叉校验。
4. 每轮打开前退出应用并确认无残留进程；同一配置运行 5 轮，取中位数。冷、温各一组。

### 6.3 10 万 commit 常驻内存

1. 以 10 万夹具启动 release exe，等图谱首帧出现后再空闲 30 s。
2. 采样（间隔 5 s，连续 3 次，记录最大值）：

```powershell
Get-Process gitdock-app | Select-Object Id, @{n='RSS_MB';e={[math]::Round($_.WorkingSet64/1MB,1)}}
Get-Process msedgewebview2 -ErrorAction SilentlyContinue |
  Measure-Object WorkingSet64 -Sum
```

3. **口径**：F1-1 的「常驻内存」= `gitdock-app` 主进程 `WorkingSet64` + 该应用创建的 `msedgewebview2` 子进程 `WorkingSet64` 之和。WebView2 为共享进程模型，若同机存在其他 WebView2 应用必须按 `ParentProcessId` 过滤或换干净环境，否则数字不可用。
4. 通过阈值：合计 ≤ 500 MB @ 10 万 commit。同时记录 5 万夹具的一组数值作参考。

- 首屏判定：5 轮中位数 ≤ 1500 ms 为通过。

测量注记：

- 本轮两个夹具的冷/温中位数差均 < 25 ms，说明首屏时间被 release 进程启动与 WebView2 初始化主导（约 0.9 s 地板），10 万条索引的冷构建被页大小与虚拟滚动吃掉。
- perf-100k 冷启动第 1 轮 1883.5 ms 为孤立高值（该轮首次创建独立 WebView2 用户数据目录），其余 4 轮在 993–1039 ms；按方法取中位数，并保留原值以便复核。
- 内存为图谱首帧后空闲 30 s 的 3 次采样（间隔 5 s）：100k 合计 417.4 / 448.6 / 457.5 MB，主进程 34.0–34.6 MB，`msedgewebview2` 383.4–422.9 MB；50k 三次均为 439.2 MB。
- 采样期间同机另有 GitDock release 实例在运行：内存按被测进程的 `ParentProcessId` 只累计其 `msedgewebview2` 后代；图谱索引磁盘缓存不隔离，冷启动口径为删除共享的 `graph-index` 目录后测量。
- 两个夹具的 100k 输出目录 `target/test-fixtures/perf-100k/perf` 为一次性生成物，不提交仓库；测量结束后已从 `%APPDATA%\com.gitdock.desktop\settings.json` 的 `recent_repositories` 中移除验证用路径。
